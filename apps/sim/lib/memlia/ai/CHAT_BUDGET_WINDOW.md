# Lecture canonique de la fenêtre Chat

`readChatBudgetWindow({windowId,windowVersion,model})` observe uniquement la fenêtre explicitement choisie par la composition serveur. Il utilise la connexion primaire native Sim et le schéma `memliaChatCostWindow` existant, sans migration, création de politique ou lecture sur réplique. La sélection est copiée par le sérialiseur JSON strict borné avant la première attente ; champs supplémentaires/getters/identifiants ou versions invalides refusés sans coercition.

Un unique SELECT exige l'ID exact, la version entière exacte, `state=open`, `currency=USD` et la période active selon `clock_timestamp()` PostgreSQL. Il ne sélectionne jamais une autre fenêtre ou une première ligne arbitraire. Seul le JSONB `pricingProfile` est projeté, validé et figé par `captureChatPricingProfile` déjà intégré. Son modèle doit égaler la sélection. NULL, profil malformé, modèle différent, fenêtre absente/fermée/périmée/future ou erreur DB donnent le seul message `Chat budget window is unavailable.`, sans cause/SQL/valeur brute.

Le résultat figé `{windowId,windowVersion,pricingProfile}` est une **observation de métadonnées**, sans principal ou autorité. Ce helper ne choisit pas une clé, n'envoie aucun appel, ne réserve aucune somme et ne contrôle pas le solde. Il ne déduit aucune autorisation d'une référence fournie par le navigateur ; son futur appelant doit utiliser la configuration administrateur validée et les droits natifs. Le catalogue et le tarif physique sont revalidés par le provider budgété existant avant chaque tentative.

La fenêtre peut changer après cette lecture. La réservation native après COMMIT doit toujours relire/verrouiller la version, le profil canonique, la période et le budget. Le profil capturé n'est pas une réservation ni une révocation atomique garantie. Aucun Chat HTTP activé dans cette tranche.

Le test `chat-budget-window.integration.test.ts` utilise les guards natifs vers la seule DB jetable budget et deux rôles distincts : web pour le code lu, administrateur existant pour les seules fenêtres fictives UUID de la recette. PostgreSQL, SELECT, JSONB, dates et fermetures des pools sont réels ; aucun SQL/permission/horloge n'est doublé. Les modèles/prix sont des fixtures sans fournisseur réel. Pas de DDL, GRANT, migration, user/workspace ou réservation créés. Les neuf cas couvrent sélection/capture, absence/version/modèle, état fermé, périodes, profils manquants/malformés/divergents et getter/champ supplémentaire. Ils ne qualifient ni une route HTTP, ni la source POSIX Linux, ni un envoi ou un coût IA.
